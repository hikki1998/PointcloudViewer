# 基于 Codex 搭建 Qt/C++ 点云巡检软件的过程复盘

> 这是项目过程复盘文档，不是当前仓库的日常 onboarding 主入口。首次进入仓库时优先阅读根目录 `AGENTS.md`、根目录 `CLAUDE.md` 和 `docs/agent/README.md`。

## 背景

这个项目的目标，不是单纯做一个能打开 LAS 的 demo，而是逐步搭出一个可编译、可运行、可分发，并且能承载电力巡检业务场景的桌面客户端软件。

技术路线从一开始就比较明确：

- 客户端框架：Qt 5.15.2
- 开发语言：C++17
- 构建系统：CMake
- 编译环境：Visual Studio 2022
- 点云与渲染：LASlib + OpenSceneGraph

我和 Codex 的协作方式，也不是一次性把需求全说完，而是按“先能跑，再好用，再贴业务”的顺序，持续迭代推进。

## 整体工作流

### 1. 先明确产品形态和技术栈

第一步不是直接让它写大量功能代码，而是先把这些约束定清楚：

- 软件是 Windows 桌面客户端，不是 Web
- 基于 Qt/C++ 实现
- 通过 CMake 构建
- 用 VS2022 和 Qt 5.15.2 编译
- 三方依赖优先结合本机已有环境和仓库内可分发内容处理

这一步的价值在于，Codex 一旦知道了边界条件，后面做项目结构、CMake、部署、运行时依赖收集时会稳定很多。

### 2. 先做一个能加载和渲染 LAS 的最小可运行版本

第二步是让它先搭出主链路：

- 能创建 Qt 工程
- 能接入点云读取
- 能把 LAS 数据加载到场景里
- 能完成基本渲染与视图显示

这一阶段的重点不是业务功能，而是验证“项目骨架是成立的”。只要主窗口、渲染窗口、LAS 读取和基础交互跑通，后面的功能扩展才有意义。

### 3. 补齐构建、部署和运行时依赖

最小版本出来以后，我没有停留在“能在开发机上打开”的程度，而是继续推动它把工程化部分补全：

- CMake 中加入运行时依赖部署
- 编译完成后自动拷贝 Qt 依赖
- 自动收集 OSG 和其他三方 DLL
- 处理翻译文件生成和部署
- 让最终构建结果尽量接近“一键运行”

这一步很关键。很多 AI 产出的 C++ 项目，能生成代码，但不一定能真正跑起来。这里 Codex 的工程能力表现比较突出，能把“编译成功”和“运行成功”之间那段经常最麻烦的工作补上。

### 4. 建立版本库和基本协作基线

在项目能编译、能运行之后，再进入仓库化和持续迭代阶段：

- 建立仓库
- 提交初版
- 补充 README、上下文和开发指引
- 固化标准构建和 smoke test 路径

这一步的意义在于，把项目从“单次生成结果”变成“可持续维护的代码库”。

### 5. 从通用点云查看器向业务软件演进

基础稳定之后，后面的推进思路就比较清晰了：不断从通用功能走向巡检业务能力。

包括但不限于：

- 多数据集加载与项目树管理
- 点云显示参数控制
- 量测与剖面分析
- 杆塔标记与编辑
- 隐患标注与台账
- 风险分析
- 巡检航线规划
- KML / KMZ / DJI 相关导出能力

这部分不是一次性设计完，而是我不断根据实际方向追加需求，Codex 负责快速实现、编译验证、再进入下一轮迭代。

## 我是如何一步步引导 Codex 的

从这段时间的使用来看，比较有效的引导方式主要有下面几条。

### 1. 先给明确边界，再让它执行

例如一开始就把这些信息讲清楚：

- 用什么 Qt 版本
- 用什么编译器
- 用什么构建系统
- 希望输出成什么样的软件

这比上来只说“做个点云软件”效果好很多。

### 2. 先要求打通主链路，不急着堆功能

我不是一开始就让它做复杂业务，而是先让它把下面这些关键链路打通：

- 工程创建
- 构建成功
- 运行成功
- LAS 能加载
- 场景能渲染

这样做的好处是，出了问题时更容易定位，也不容易把复杂功能叠加在一个不稳定底座上。

### 3. 对工程化要求要明确提出来

如果不主动要求，AI 往往更关注“写出功能代码”，但桌面软件的实际难点很多在工程层：

- 运行时依赖
- 资源打包
- 翻译部署
- 构建输出目录
- smoke test

我会明确要求它把这些也做掉，这样最终产物才更接近可交付的软件，而不是只能在作者机器上运行的代码片段。

### 4. 需求要分阶段推进，不要一次塞满

比较有效的方式是：

1. 先做基础能力
2. 再补交互体验
3. 再补工程与验证
4. 再叠加业务功能
5. 最后处理性能和细节优化

这样 Codex 的输出稳定性会明显更高，也更容易回退和修正。

### 5. 对结果要用“能不能用”来验收

我这边的验收标准通常不是“代码看起来像实现了”，而是：

- 能不能编译
- 能不能运行
- 功能是不是可操作
- UI 有没有明显 usability 问题
- 回归有没有破坏原能力

这点很重要。对桌面软件来说，很多问题不是逻辑错误，而是交互状态、部署、控件状态、窗口行为这些真实使用问题。

## Codex 在这个项目里的优点

### 1. 编码速度和执行力强

对明确需求的响应速度很快。尤其在 C++ / Qt 这种传统客户端开发场景里，能持续输出可编译代码，这一点还是比较难得的。

### 2. 工程能力比预期好

不只是写业务逻辑，还能处理：

- CMake
- 依赖收集
- 运行时部署
- 构建目录组织
- 文档和上下文梳理

这使得它更像一个“能落地的开发搭子”，而不只是代码补全工具。

### 3. 对多轮迭代适应性不错

项目不是静态题目，而是持续变化的。Codex 在这种“先搭起来，再不断调整方向”的过程中，整体适应性还可以。

## 当前体验到的不足

### 1. 成本和限额压力比较大

高能力模型效果明显更好，但限额和成本都比较高。上下文也不是无限的，复杂项目做久了还是会顶到边界。

### 2. 会话连续性仍然有限

一段时间不用就可能要重新接续上下文，恢复状态会花时间。对于长期项目来说，这个问题会放大。

### 3. 使用环境有限制

当前依赖外网环境，内网场景下不方便，这对企业或受限开发环境会有明显影响。

### 4. 对深业务优化还需要更多真实反馈

目前完成得比较好的，更多还是通用产品能力和中等复杂度业务能力。像真正的大点云性能优化、深业务规则、复杂作业闭环，仍然需要更强的人工引导和更多迭代。

例如大 LAS 加载性能，目前已经讨论过方向，也做过尝试，但体感优化还没有达到理想状态，这类问题明显比普通功能开发更难。

## 当前阶段的结论

如果把这次实践总结成一句话：

> Codex 很适合用来快速搭建一个有工程基础的桌面软件原型，并持续把它推进到“可运行、可维护、可扩展”的状态；但涉及高成本上下文、复杂性能优化和深业务细节时，仍然需要较强的人来持续掌舵。

对这个项目来说，它已经帮助完成了几件很有价值的事：

- 把一个 Qt/C++ 点云软件从零搭了起来
- 把构建、部署、翻译、运行这些工程链路补齐了
- 把产品从通用查看器逐步推向了电力巡检业务软件

后续如果继续推进，最值得投入的方向仍然是：

- 大数据量加载与渲染性能
- 业务功能的细化与闭环
- UI/交互细节打磨
- 更稳定的长期协作和回归验证机制
